## 1. 单仓库级噪声过滤

**为什么需要：** 现在黑名单只能按作者整账号剔除，但噪声仓库很分散——最近一次快照里 451 个判定为噪声的仓库散在 **326 个作者**名下，其中 **307 个作者只有 1 个**噪声仓库；另有 **100 个作者既有噪声仓库也有真项目**（例如 `xing-shuyin`：1 个噪声 + 2 个相关仓库，其中 `dsh-ui-tools` 有 6 星）。整账号拉黑会连真项目一起删。

**改法：** `data/noise-blacklist.json` 增加平级键 `repos`：

```json
{
  "count": 2,
  "owners": { "uckkk": { "repos": 1274, "reason": "mass-publish" } },
  "repos": { "xing-shuyin/some-noise-repo": { "note": "人工", "addedAt": "2026-10-14T00:00:00Z" } }
}
```

- 后台名单页新增"添加仓库（owner/repo）"，只剔这一个仓库，不动该作者别的项目。
- 采集器、离线重建、Node/Python 两侧都识别它；**采集器写盘时会原样保留单仓库条目**（以前只回写 `owners`，新键会被静默抹掉，这是这次一并修掉的坑）。
- `meta` 里新增 `noiseBlacklistReposSize` / `noiseReposSkipped`，方便自查。

## 2. 手动添加黑名单"无实际反馈"

**根因：** 界面其实有反馈（"已加入黑名单"），但**加完看不出任何变化**。两个原因：

1. 黑名单要等「立即应用」才重算，而**如果这个作者当前压根不在数据里，永远不会有变化**——系统当时不会告诉你这一点。
2. 真缺陷：成功分支没清掉上一次失败的红色提示条，会出现"红条 + 绿 toast 同屏"。

**改法：** 加入时后端先算**影响预估**（该作者在累积索引里的仓库数、星标合计），界面按三种情况说实话：

- 正常：`点『立即应用』后将移除 N 个仓库（合计 M star）`
- `N = 0`：`他当前不在数据里（累积索引 0 个仓库），加名单不会有可见变化`
- 重复添加：`已在黑名单里，本次只更新了备注`

同时成功时清掉旧红条。实测示例：`uckkk` → 0 个仓库（加它本来就不会有变化）；`xing-shuyin` → 3 个仓库 / 302 star。

## 3. 白名单"字符匹配" → 改成别名组

**为什么不做子串/正则匹配：** 构建流程里有一条既有判据——**挂了 ≥3 个 DSH 标签、正文又没有插件线索的仓库判为噪声**。若把匹配改成"包含 `dsh` 就算"，一个仓库的 `dsh-plugin-desktop` 会同时命中 `dsh`、`dsh-plugin`、`dsh-plugin-desktop` 三个 → `matchedTags` 从 1 变 3 → **直接误杀**。另外任意正则能把常驻采集器拖死（回溯爆炸），项目已有结论不开放。

**改法：** 白名单条目仍是**精确标签**，另外显式登记"别名组"：

```
dsh = awesome-dsh, dsh-awesome
dsh-plugin = dsh-plugin-x
```

- 左边是规范标签，必须已经在白名单里（否则整组忽略，避免凭空扩大口径）。
- 别名命中会归到规范标签上：仓库只打 `awesome-dsh`，`matchedTags` 也算 `dsh`。
- **抓取层只用规范标签**：GitHub 搜索只认精确 topic，拿别名去搜纯属白烧配额。所以别名组只影响**已经在索引里的仓库算不算 DSH**，不会让采集器抓到新仓库。
- **默认不内置任何别名组**：得由人甄别精度。本机 44,604 个仓库里，含 `dsh` 字样但不在白名单的标签有 327 种，最多的 `dsh-bundle`(243)、`dsh-skill`(226)、`awesome-dsh-plugin`(51)——但同一批候选里也混着 **`DSharpPlus`（C# 库）、`dshot`（无人机电调协议）、`dshield`（防火墙）** 这类同形异义标签，自动内置必然误伤。

## 4. 后台配额预算配置

**改法：** 11 项参数进 `data/admin/config.json` 的 `collector` 块，后台新增「设置」页：预算、单段翻页、刷新窗口、README 抓取量/摘要长度/星标门槛、releases 预算、npm 预算、轮询间隔、最小覆盖率、前端节点上限。每项显示当前值、默认值与合法范围。

**关键取舍——优先级是 后台配置 > 启动参数 > 内置默认值。** 理由：这些参数只服务本机这一个采集进程，而后台才是给人用的入口。如果让启动命令里的 `--budget 600` 压过后台，用户在后台把预算改成 200 会毫无效果——那就等于本 issue 没解决。所以启动参数退居"初始化默认值"：只在某一项**从没配置过**时才生效。

- 采集器每轮把"生效值 + 来源（后台配置 / 启动参数 / 内置默认）"写进状态文件，设置页会标出每一项的来源。
- 保存后**下一轮采集自动按新值跑**（参数每轮读一次）。白名单标签仍要重启采集器，因为规则表是进程启动时读的。
- 顺带修掉一个隐蔽问题：以前后台保存白名单会把 `config.json` 里不认识的键静默抹掉，现在未知键原样保留。

## 5. 分段配置（暂缓）

分段粒度由星标区间切片 + 按创建时间细分决定。要把它做成后台可配，必须同时提升段队列的 `SCHEMA_VERSION`，否则旧 key 会变成孤儿、**同一片空间被扫两遍**、白花配额；而升版本会**丢弃现有 539 个分段的状态重建**，下一轮请求量明显上升。

眼下配额紧张（最近一次轮询时 core 配额剩 25），所以先把参数外提的接口设计留着，等配额宽裕再做。

## 6. 顺带修掉两条"随数据刷新随机翻红"的老用例

这两条不是本 issue 要求的，但会干扰"改动到底有没有搞坏东西"的判断，所以一并修了：

- **画布命中测试取最近球**（`src/graph.js`）：原来 `pick()` 是"从后往前、第一个覆盖到点的球就返回"，结果取决于节点绘制顺序——点小球邻域时可能被判给旁边的大球。改成取**中心最近**的那个。修掉「点关联行居中后画面正中也应该是它」用例。
- **布局分离迭代按规模自适应**（`src/layout-sector.js`）：球半径固定，节点越多装得越挤，固定 110/160 次迭代在三万节点时压不住重叠（实测 5.70%，阈值 5%）。改成按节点数加迭代，**实测 5.70% → 1.99%**，代价是预计算慢约 4.7 秒（8.3s → 13.0s，纯离线一次，不进浏览器）。阈值本身没动。
